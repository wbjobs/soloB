# 游戏服务器原型 - ECS架构

这是一个使用Go语言和ECS（Entity-Component-System）架构构建的简易游戏服务器原型。

## 项目结构

```
b35/
├── components/
│   └── components.go    # 定义所有ECS组件
├── events/
│   └── event_bus.go     # 事件总线系统
├── spatial/
│   └── grid.go          # 空间分区系统（性能优化）
├── systems/
│   └── systems.go       # MovementSystem和EventSystem
├── go.mod               # Go模块配置
├── main.go              # 主程序入口
└── README.md            # 项目说明
```

## 功能特性

### 1. ECS核心

**组件定义**：
- `Position`: 表示实体的位置（X, Y坐标）
- `Health`: 表示实体的生命值（当前值、最大值）
- `Inventory`: 表示实体的物品栏（物品到数量的映射）
- `Player`: 表示玩家身份（玩家名称）
- `WorldEvent`: 表示世界事件（类型、影响半径、持续时间）

### 2. 动态事件系统

**事件总线** (`EventBus`)：
- 支持事件订阅 (`Subscribe`)
- 支持事件发布 (`Publish`)
- 支持事件类型区分

**EventSystem**：
- 周期性地（默认5秒，可配置）在随机位置生成世界事件
- 支持的事件类型：
  - 矿脉刷新
  - 怪物入侵
  - 宝箱出现
  - 神秘商人到访
- 计算事件影响范围内的玩家
- 通过事件总线广播事件通知

### 3. MovementSystem

- 周期性地更新所有带有Position组件的实体位置
- 模拟实体的随机移动

### 4. 事件阶段系统

每个世界事件现在包含四个阶段：

**预警阶段 (EventPhaseWarning)**
- 事件创建后立即进入
- 在地图上标记事件区域（通过事件总线广播位置信息）
- 向附近玩家发送预警消息，提示事件即将发生
- 普通事件：10秒预警 | 怪物入侵：15秒预警

**开始阶段 (EventPhaseActive)**
- 预警结束后自动进入
- 执行事件特定逻辑：
  - **怪物入侵**：在事件范围内随机生成5-10个怪物实体
  - **其他事件**：直接进入激活状态
- 普通事件：40秒持续 | 怪物入侵：60秒持续

**结束阶段 (EventPhaseEnding)**
- 事件持续时间结束后进入
- 开始结算过程，计算奖励
- 向附近玩家发送结算通知
- 持续10-15秒

**已结束阶段 (EventPhaseEnded)**
- 事件完全结束
- 向在事件范围内的玩家发放奖励
  - 矿脉刷新：铁矿 x10, 金矿 x5
  - 怪物入侵：金币 x100, 经验值 x200, 稀有材料 x1
  - 宝箱出现：金币 x50, 随机道具 x3
  - 神秘商人到访：折扣券 x1, 稀有商品 x2
- 清理怪物实体
- 从世界中移除事件实体

## 运行项目

### 前置要求

- Go 1.21 或更高版本

### 安装依赖

```bash
go mod download
```

或

```bash
go get github.com/mlange-42/arche/ecs
```

### 运行服务器

```bash
go run main.go
```

## 技术栈

- **语言**: Go 1.21
- **ECS框架**: [arche](https://github.com/mlange-42/arche)
- **架构模式**: Entity-Component-System

## 设计说明

### ECS架构优点

1. **数据局部性**: 相同类型的组件存储在连续内存中，提高缓存命中率
2. **灵活性**: 通过组合组件而非继承来定义实体类型
3. **可扩展性**: 易于添加新组件和系统
4. **性能**: 系统可以高效地遍历和处理实体

### 事件总线设计

- 采用发布-订阅模式
- 事件处理器是函数类型，易于扩展
- 支持向特定目标玩家发送消息

### EventSystem 工作流程

1. 检查是否到达事件生成间隔
2. 生成随机位置和随机事件类型
3. 创建世界事件实体
4. 查询所有玩家实体
5. 计算玩家与事件位置的距离
6. 识别在影响范围内的玩家
7. 通过事件总线发布事件通知

## 性能优化

### 问题分析

原始实现中，EventSystem存在O(N*M)的复杂度问题：
- **N**：事件数量
- **M**：玩家数量

当多个事件同时存在且有大量玩家时，每个事件都需要遍历所有玩家计算距离，导致严重的性能问题。

### 优化方案

#### 1. 空间分区（Spatial Grid）

**新增 `spatial/grid.go` 实现了网格空间分区系统：

- 将游戏世界划分为固定大小的单元格
- 每个玩家根据位置插入到对应的网格单元
- 查询时只检查事件位置周围的少数几个网格，而不是所有玩家
- 使用平方距离避免开方运算（避免开方运算
- 复杂度降低到O(N * K)，其中K远小于M

**关键优化：
```
原来：每个事件检查所有玩家
现在：每个事件只检查事件附近几个网格内的玩家
```

#### 2. 事件生命周期管理

**EventInstance 结构体：
- 维护已通知的玩家集合（Notified map）
- 避免重复通知
- 事件过期后自动清理

#### 3. 延迟更新机制

**帧间隔更新：
- 每3帧才执行一次空间网格重建和事件处理
- 并非每一帧都执行事件处理
- 避免过度计算

#### 4. 事件清理机制

- 事件超过持续时间后自动从世界中移除
- 清理不再需要的事件实体
- 释放内存

### 优化前后性能对比

| 场景 | 优化前 | 优化后 |
|--------|--------|--------|
| 1000玩家 + 10事件 | 10,000次距离计算 | ~10 * 100次距离计算 |
| 10000玩家 + 50事件 | 500,000次距离计算 | ~50 * 200次距离计算 |
| 玩家移动频繁 | 每次更新重建网格 | 每3帧重建网格 |

### 可调节参数

在 `systems/systems.go` 中可以调整：
- `cellSize`：网格单元大小（默认25）
- `updateInterval`：事件处理间隔（默认3帧）
- `WorldBounds`：世界边界（默认100x100）

## 扩展建议

1. **添加更多组件**: 如 `Velocity`（速度）、`Attack`（攻击属性）等
2. **添加更多系统**: 如 `CombatSystem`（战斗系统）、`InventorySystem`（物品系统）
3. **网络功能**: 集成WebSocket或TCP服务器，支持客户端连接
4. **持久化**: 添加数据存储功能
5. **配置文件**: 将事件间隔、事件类型等配置外部化
